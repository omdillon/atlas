## 1. Overview

### 1.1 Purpose

This document defines the requirements for the **Smart Interface** phase of the prosthetic hand project. The system provides a wireless, browser-based tool for a developer to monitor real-time myoelectric telemetry from the prosthetic hand, dynamically calibrate motor and control parameters, and flash updated firmware to the ESP32 microcontroller — all without a USB cable or serial connection.

### 1.2 Scope

This PRD covers three tightly coupled components:

- **ESP32 firmware layer** — BLE GATT server, telemetry packaging, OTA receive handler
- **BLE transport layer** — GATT service/characteristic architecture and packet schema
- **Web application** — Web Bluetooth client, real-time dashboard, calibration controls, OTA uploader

It does not cover embedded intent decoding (Phase 3), PID positional control (Phase 2), or clinical calibration protocols (Phase 5). Those are addressed in separate phase PRDs.

### 1.3 Hardware Platform

| Component | Detail |
|---|---|
| Microcontroller | ESP32 (dual-core, 240 MHz) |
| Motor drivers | DRV8214 × 5 (one per finger) |
| EMG sensors | Gravity Analog EMG × 4 channels |
| Firmware toolchain | PlatformIO (VS Code), Arduino framework |
| Target browser | Chrome 89+ (Web Bluetooth API) |

### 1.4 Key Design Constraints

- Web Bluetooth is only available in Chromium-based browsers over HTTPS or `localhost`
- BLE ATT MTU is negotiated at runtime; design assumes a minimum of 23 bytes, target 512 bytes post-negotiation
- The web app must be deployable as a static site (GitHub Pages) with no build step and no backend server
- All OTA `.bin` files are generated by PlatformIO and located at `.pio/build/<env>/firmware.bin` after a successful build

## 2. User Roles

### Developer / Engineer (primary user)

Uses the interface during active firmware development to:

- Debug motor stalls and verify ripple-count behaviour across all 5 motors
- Observe raw and MAV-filtered EMG signals from all 4 channels in real time
- Tune PID constants and EMG threshold parameters without recompiling
- Flash updated firmware builds wirelessly to avoid repeated USB reconnection

### Clinician / Researcher (future user — Phase 5)

Not in scope for this phase. Architecture decisions should not preclude a future clinician-facing view being added as a separate tab or route in the same web app.

## 3. Objectives and Success Metrics

| Objective | Success Metric |
|---|---|
| Real-time telemetry visualisation | EMG and ripple-count data renders at 20–30 Hz without dropped frames or UI jank |
| Dynamic parameter calibration | A parameter write from the browser is reflected in ESP32 behaviour within 100 ms |
| Wireless OTA flashing | A full firmware image flashes successfully over BLE with no USB cable, completing within 3 minutes for a typical 1 MB binary |

| Zero-install deployment | The web app opens directly in Chrome from a GitHub Pages URL with no npm install, no local server, and no extensions |

## 4. System Architecture

### 4.1 Layer Overview

The system is decomposed into three layers with clean interfaces between them. The ESP32 firmware is never aware of the web app's UI; the web app is never aware of motor hardware. The BLE transport is the sole contract.

```
┌─────────────────────────────────────────────────────┐
│                   Web Application                    │
│   BLE Manager │ Telemetry Parser │ Dashboard │ OTA  │
└──────────────────────┬──────────────────────────────┘
                       │  Web Bluetooth API
┌──────────────────────▼──────────────────────────────┐
│                  BLE Transport                       │
│  Telemetry char. │ Command char. │ OTA char.         │
└──────────────────────┬──────────────────────────────┘
                       │  GATT (BLE 4.2+)
┌──────────────────────▼──────────────────────────────┐
│               ESP32 Firmware                         │
│  Core 0: EMG · Ripple · PID · Stall                 │
│  Core 1: GATT Server · Cmd Parser · OTA Handler     │
└─────────────────────────────────────────────────────┘
```

### 4.2 ESP32 Dual-Core Split

The ESP32's dual-core architecture is exploited to prevent BLE stack activity from interfering with hard real-time motor control.

**Core 0 — Real-time loop**

- ADC sampling of all 4 EMG channels
- MAV (Mean Absolute Value) feature extraction per channel
- Ripple counting via DRV8214 on all 5 motor channels
- PID positional control loop
- Stall detection (inrush window + ripple-count delta)
- Telemetry frame assembly into a shared FreeRTOS queue

**Core 1 — BLE stack**

- GATT server lifecycle (advertising, connection, MTU negotiation)
- Telemetry notification scheduler (pulls from inter-core queue, paces at 20–30 Hz)
- Command characteristic write handler (parses and applies calibration params)
- OTA characteristic write handler (`Update.h` chunk reassembly and verification)
- Failsafe watchdog (brakes all motors if BLE connection is lost unexpectedly)

**Inter-core communication:** A FreeRTOS queue (`xQueueSend` / `xQueueReceive`) passes the assembled telemetry frame from Core 0 to Core 1. Queue depth of 4 frames prevents Core 0 from blocking if Core 1 is momentarily busy with a BLE event.

### 4.3 GATT Service Architecture

All characteristics live under a single custom service UUID.

| Characteristic | Operation | Max length | Purpose |
|---|---|---|---|
| `TELEMETRY_CHAR_UUID` | NOTIFY | 20 bytes | ESP32 → Browser: real-time sensor frame |
| `COMMAND_CHAR_UUID` | WRITE | 64 bytes | Browser → ESP32: parameter updates |
| `OTA_CHAR_UUID` | WRITE | 512 bytes | Browser → ESP32: firmware chunks |

UUIDs should be generated once as custom 128-bit UUIDs and hardcoded in both the firmware and web app.

### 4.4 Telemetry Packet Schema

The telemetry frame is packed as a binary `Int16Array` (little-endian) to minimise BLE bandwidth. At 25 Hz, this yields approximately 500 bytes/second — well within BLE 4.2 throughput limits.

```
Byte offset  Field               Type      Notes
0–1          EMG channel 0       int16     Raw ADC value
2–3          EMG channel 1       int16     Raw ADC value
4–5          EMG channel 2       int16     Raw ADC value
6–7          EMG channel 3       int16     Raw ADC value
8–9          MAV channel 0       int16     Scaled ×100 (fixed-point)
10–11        MAV channel 1       int16     Scaled ×100
12–13        MAV channel 2       int16     Scaled ×100
14–15        MAV channel 3       int16     Scaled ×100
16–17        Ripple count M1     int16     Motor 1 cumulative count
18–19        Ripple count M2     int16     Motor 2
20–21        Ripple count M3     int16     Motor 3
22–23        Ripple count M4     int16     Motor 4
24–25        Ripple count M5     int16     Motor 5
26           Stall flags         uint8     Bitmask: bit N = motor N stalled
27           System event        uint8     0=none, 1=grip triggered, 2=reset
```

Total: **28 bytes** per frame.

### 4.5 Command Packet Schema

Commands from the browser are also packed binary, prefixed with a 1-byte command ID.

```
Byte 0       Command ID          uint8
Byte 1–N     Payload             varies
```

| Command ID | Name | Payload |
|---|---|---|
| `0x01` | Set KMC | `uint8 motor_id, uint8 kmc_value` |
| `0x02` | Set KMC scale | `uint8 motor_id, uint8 scale (1–4)` |
| `0x03` | Set inrush duration | `uint8 motor_id, uint16 ms` |
| `0x04` | Set brake threshold | `uint8 motor_id, uint16 threshold` |
| `0x05` | Set EMG min/max | `uint8 channel, int16 min, int16 max` |
| `0x06` | Set PID constants | `uint8 motor_id, float Kp, float Ki, float Kd` |
| `0x10` | Trigger grip | `uint8 grip_id (0=open, 1=power, 2=tripod, 3=lateral)` |
| `0x11` | Zero ripple counters | `uint8 motor_mask (bitmask)` |
| `0x20` | OTA begin | `uint32 total_size` |
| `0x21` | OTA abort | _(no payload)_ |

### 4.6 OTA Flashing Flow

1. User builds firmware in PlatformIO (`pio run`)
2. User opens the OTA tab in the web app and clicks **Select firmware**
3. Browser file picker opens; user selects `.pio/build/<env>/firmware.bin`
4. Web app sends command `0x20` (OTA begin) with total file size
5. ESP32 calls `Update.begin(total_size)` and acknowledges via a response notification
6. Browser slices the `.bin` into 512-byte chunks and writes each to `OTA_CHAR_UUID` sequentially
7. ESP32 calls `Update.write(chunk)` for each received chunk
8. After the final chunk, ESP32 calls `Update.end()`, verifies the image, and reboots
9. Web app detects BLE disconnection (expected post-reboot) and displays **Flash complete — reconnect**

**Error handling:** If `Update.hasError()` returns true at any point, the ESP32 sends an error event via the telemetry characteristic's system event byte, and the web app displays the error and aborts the sequence. The user can retry without power-cycling the device.

## 5. Functional Requirements

### 5.1 Connection Management

- **FR-CON-01:** The web app shall provide a Connect button that initiates a BLE device scan filtered to the prosthetic hand's service UUID
- **FR-CON-02:** The web app shall display connection state: `Disconnected` / `Connecting` / `Connected` with RSSI indicator
- **FR-CON-03:** On successful connection, the web app shall negotiate the maximum available ATT MTU (target 512 bytes for OTA)
- **FR-CON-04:** On unexpected disconnection, the web app shall freeze all live charts, display a prominent `Connection lost` banner, and attempt one automatic reconnect after 3 seconds

### 5.2 Telemetry Dashboard

- **FR-TEL-01:** The dashboard shall display a scrolling oscilloscope for each of the 4 raw EMG channels, with configurable time window (default 5 seconds)
- **FR-TEL-02:** The dashboard shall overlay the MAV-filtered signal on each EMG oscilloscope in a distinct colour
- **FR-TEL-03:** The dashboard shall display a real-time bar or line chart showing the current ripple count for each of the 5 motors
- **FR-TEL-04:** The dashboard shall display an event log (fixed-height scrolling console) showing discrete system events with timestamps: stall detections, grip triggers, resets, and OTA events
- **FR-TEL-05:** The dashboard shall display the current BLE notification rate (Hz) as a live readout to confirm the 20–30 Hz target is being met

### 5.3 Calibration Controls

- **FR-CAL-01:** The calibration panel shall provide per-motor sliders or numeric inputs for: KMC (0–255), KMC scale (1–4), inrush duration (ms), and brake threshold
- **FR-CAL-02:** The calibration panel shall provide per-channel inputs for EMG minimum (noise floor) and maximum (saturation) thresholds
- **FR-CAL-03:** The calibration panel shall provide per-motor inputs for PID constants Kp, Ki, and Kd
- **FR-CAL-04:** All calibration changes shall be sent to the ESP32 immediately on user commit (slider release or input blur), not batched
- **FR-CAL-05:** The calibration panel shall display the last-acknowledged value received from the ESP32 alongside each control, so the user can confirm the write succeeded

### 5.4 Manual Overrides

- **FR-OVR-01:** The override panel shall provide buttons to trigger each named grip state: Open, Power grip, Tripod grip, Lateral grip
- **FR-OVR-02:** The override panel shall provide a per-motor or all-motors Zero ripple counters button
- **FR-OVR-03:** Override commands shall be sent immediately on button press with no confirmation dialog (developer tool context)

### 5.5 OTA Firmware Uploader

- **FR-OTA-01:** The OTA tab shall provide a file picker (`<input type="file" accept=".bin">`) for selecting the firmware binary
- **FR-OTA-02:** After file selection, the web app shall display the filename and file size before flashing begins
- **FR-OTA-03:** The web app shall display a progress bar showing bytes transferred / total bytes during flashing
- **FR-OTA-04:** The web app shall display estimated time remaining during flashing based on current throughput
- **FR-OTA-05:** On completion, the web app shall display a success message and prompt the user to reconnect
- **FR-OTA-06:** The OTA tab shall be disabled (greyed out) unless the BLE connection is active

## 6. Non-Functional Requirements

### 6.1 Performance

- **NFR-PERF-01:** The telemetry parser and chart update pipeline shall process each incoming BLE notification within 50 ms to maintain apparent real-time rendering at 25 Hz
- **NFR-PERF-02:** OTA throughput shall sustain a minimum of 6 KB/s over BLE, targeting completion of a 1 MB binary within 3 minutes
- **NFR-PERF-03:** The web app shall remain responsive (no UI blocking) during active OTA flashing; dashboard charts shall continue updating if telemetry notifications are still arriving

### 6.2 Reliability and Safety

- **NFR-REL-01:** If the BLE connection drops during OTA flashing, the ESP32 shall not apply a partial firmware image. `Update.abort()` must be called on connection loss
- **NFR-REL-02:** The ESP32 failsafe watchdog on Core 1 shall apply brakes to all motors within 500 ms of an unexpected BLE disconnection
- **NFR-REL-03:** The web app shall never send a parameter write during an active OTA flash sequence; the calibration and override panels shall be disabled during flashing

### 6.3 Deployability

- **NFR-DEP-01:** The web app shall be a single self-contained `.html` file with all CSS and JS inlined or loaded from a CDN — no build step, no `node_modules`, no local server required
- **NFR-DEP-02:** The web app shall be deployable to GitHub Pages and function correctly over HTTPS (required by Web Bluetooth)
- **NFR-DEP-03:** The web app shall function correctly on localhost for development use without HTTPS

### 6.4 Browser Compatibility

- **NFR-BRW-01:** The web app shall target Chrome 89+ and Edge 89+ (both support Web Bluetooth). Firefox and Safari are explicitly out of scope (no Web Bluetooth support)
- **NFR-BRW-02:** The web app shall display a clear unsupported browser message if `navigator.bluetooth` is not available

| Parameter | Default value | Notes |

## 8. Open Design Questions

| # | Question | Impact |
|---|---|---|
| 1 | Should the web app persist calibration profiles to `localStorage` so settings survive a page refresh? | Medium — useful for dev sessions, trivial to implement |
| 2 | Should the telemetry frame include a sequence number for dropped-packet detection? | Low — adds 2 bytes; useful for diagnosing BLE reliability |
| 3 | What is the correct ATT MTU negotiation behaviour on the ESP32 Arduino framework — does `BLEDevice::setMTU()` need to be called explicitly? | High — affects OTA chunk size and throughput |
| 4 | Should each motor's ripple count be an absolute cumulative value or a delta since last notification? | Medium — cumulative is simpler to chart; delta may overflow int16 at high speeds |
| 5 | Should the OTA characteristic use INDICATE (acknowledged) rather than WRITE WITHOUT RESPONSE to guarantee chunk delivery ordering? | High — determines whether software-level ACK/retry logic is needed |

## 9. Development Phases

### Phase 1A — BLE skeleton (current)
ESP32 GATT server with all three characteristics wired up. Telemetry sends stub data (counter values). Web app connects and parses the frame. OTA characteristic accepts writes and logs them without flashing. Goal: validate the full BLE pipeline end-to-end.

### Phase 1B — Live telemetry
Wire Core 0 ADC reads and DRV8214 ripple counts into the telemetry frame. Oscilloscope and ripple-count charts live in the web app. Stall events visible in the event log.

### Phase 1C — Calibration writes
Command characteristic handler parses and applies all calibration commands. Web app calibration panel is functional. Round-trip confirmation (ESP32 echoes accepted values) is verified.

### Phase 1D — OTA
Full OTA flash flow implemented and tested end-to-end. Chunking, progress reporting, error handling, and post-flash reconnect all verified.

### Phase 1E — Hardening
Session stability testing (30-minute continuous run). Edge cases: BLE drop during OTA, invalid command payloads, motor stall during calibration write, browser tab backgrounded during flash.

## 10. Future Scope (Phase 2+)

The following are explicitly out of scope for this PRD but should be kept in mind as architectural constraints:

- **Abstract decoder visualiser** — 2D MCI cursor space rendered in the web app, replicating the Dyson 2018 centre-out task. Will require a new NOTIFY characteristic streaming normalised muscle activation vectors.
- **Session recording and CSV export** — Logging telemetry frames to an in-memory buffer with download-as-CSV. Straightforward addition to the web app; no firmware changes required.
- **Clinician view** — A simplified, non-technical tab showing EMG amplitude as a percentage of maximum voluntary contraction, grip state, and a per-session fatigue indicator. Requires the same telemetry stream; different rendering only.
- **IMU integration** — Adding a MPU6050 over I²C to Core 0. Arm orientation data would be packed into the telemetry frame as two additional `int16` fields (roll, pitch) with minimal firmware changes.
- **Multi-device support** — Currently the web app connects to one ESP32. Future: a device selector allowing a clinician to switch between multiple hands in a lab setting.
